# ZERO Environment Rollout Protocol v0.1

## Objective

Extend ZEROCODE across the working environment without turning every surface into the same context.

ZERO must become a consistent operational layer while preserving scope isolation.

## Core principle

Global behavior may be shared.
Domain knowledge must remain scoped.

Do not inject all rules everywhere at once.

## Rollout order

### Phase 0 — Canonical Core
Status: ACTIVE

Surfaces:
- luqmanwah/zerocode
- Codex $zero skill
- global Codex bootstrap
- ChatGPT personalization routing

Shared rules:
- ZEROLINE
- context routing
- retrieval-before-inference
- resource policy
- quality gate
- Last Known Good
- Luqman final authority
- NARA protected

### Phase 1 — ChatGPT General Workbench

Inject only:
- objective-first routing
- context isolation
- latest explicit instruction precedence
- research != canon
- professional firewall
- minimal resource principle

Do not inject project-specific rules globally.

### Phase 2 — Professional Work Chats

For each work chat/project:
- identify project scope;
- identify approved standards;
- identify hardlines;
- inject only those project-specific rules;
- keep internal AI architecture terminology out unless explicitly relevant;
- verify one representative task before promoting the rule set.

### Phase 3 — Research Chats

Inject:
- research/canon separation;
- hypothesis tracking;
- source precedence;
- historical/superseded lineage;
- promotion requires validation/approval.

Do not let exploratory rules become global behavior silently.

### Phase 4 — AOA/PYXIS Lab

Inject only AOA/PYXIS-specific rules into the AOA/PYXIS scope.

Keep:
- canonical decisions
- research
- historical lineage
- protected entities

Do not leak AOA/PYXIS lab semantics into unrelated professional work.

### Phase 5 — Runtime / Infrastructure

Optional adapters:
- Zeabur
- OpenClaw
- InsForge
- future MCP/relay systems

Activate only after a concrete bottleneck exists.

Infrastructure never defines ZERO identity.

## Rule injection unit

Each injected rule must have:

- RULE_ID
- SCOPE
- PURPOSE
- TRIGGER
- BEHAVIOR
- EXCLUSIONS
- PRECEDENCE
- VERIFY
- ROLLBACK

## Promotion states

A rule moves through:

DRAFT
-> TEST
-> VERIFIED
-> ACTIVE

Optional:
SUPERSEDED
RETIRED

No rule becomes ACTIVE only because it was discussed repeatedly.

## Verification

After each rule injection:

1. run one positive test;
2. run one isolation test;
3. check for context bleed;
4. check for conflict with newer explicit user instruction;
5. check for unwanted verbosity/resource expansion;
6. if failed, roll back only that rule.

## Chat rule

A work chat receives only:
- global ZERO behavioral rules;
- its own project/scope rules;
- explicitly requested cross-scope context.

It must not inherit unrelated projects.

## Success criterion

ZERO is considered optimized across the environment when:
- the same invocation principles hold everywhere;
- each surface loads only relevant context;
- project rules remain isolated;
- retrieval works when needed;
- optional infrastructure stays optional;
- a rule can be rolled back independently.
